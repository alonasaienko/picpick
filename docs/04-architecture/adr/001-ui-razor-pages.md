# ADR-001: UI на Razor Pages замість SPA

## Контекст і проблема (Context and Problem Statement)

PicPick — вебзастосунок, у якому фотограф створює галереї й завантажує фото, а клієнт за приватним посиланням переглядає прев'ю, ставить лайки та відправляє вибір. Команді потрібно підготувати документацію та мінімальний працюючий прототип. Основний критерій вибору інтерфейсу — спростити розробку, інтеграцію та запуск проєкту.

Для цих сценаріїв потрібні форми, список і деталі галерей, перегляд прев'ю та кілька інтерактивних дій. Складний стан інтерфейсу між багатьма екранами й робота без мережі не входять до погодженого обсягу. Обираємо спосіб побудови інтерфейсу з урахуванням цих потреб і вже погодженого ASP.NET Core Web App.

## Розглянуті варіанти (Considered Options)

**SPA (Single Page Application)** — застосунок, у якому JavaScript у браузері формує й оновлює інтерфейс, керує переходами та отримує дані через API. Після початкового завантаження переходи зазвичай не потребують отримання нової HTML-сторінки від сервера. Для порівняння розглядаємо React, Angular або Vue з ASP.NET Core REST API.

**Razor Pages із серверним рендерингом** — підхід, у якому Web App формує HTML на сервері й повертає готову сторінку браузеру. Обробники сторінок приймають форми, а невеликі фрагменти JavaScript можуть окремо оновлювати частини інтерфейсу через REST API.

**ASP.NET Core MVC (Model–View–Controller)** також може формувати HTML на сервері, але розділяє обробку запитів, дані та представлення між контролерами, моделями й Razor views. На відміну від Razor Pages, обробники запитів розміщуються в контролерах, а не в `PageModel` відповідної сторінки. Підхід описано в [огляді MVC від Microsoft](https://learn.microsoft.com/en-us/aspnet/core/mvc/overview?view=aspnetcore-8.0).

**Blazor** дозволяє будувати інтерфейс із Razor-компонентів на C#. Для інтерактивного відбору порівнюємо два режими: Interactive Server, де події й оновлення проходять через з'єднання SignalR, та Interactive WebAssembly, де компоненти виконуються в браузері після завантаження середовища .NET. Blazor також підтримує статичний серверний рендеринг; постійне з'єднання потрібне саме для серверної інтерактивності. Відмінності пояснено в документації [режимів рендерингу](https://learn.microsoft.com/en-us/aspnet/core/blazor/components/render-modes?view=aspnetcore-8.0) та [моделей виконання Blazor](https://learn.microsoft.com/en-us/aspnet/core/blazor/hosting-models?view=aspnetcore-8.0).

| Варіант | Переваги для PicPick | Недоліки для PicPick |
|---|---|---|
| SPA + REST API | Зручна основа для складної взаємодії та збереження стану між екранами; інтерфейс можна розвивати окремо від серверної частини; доступні готові компоненти обраного фреймворку. | Додає окремий клієнтський проєкт, залежності й процес збирання; потрібно узгоджувати маршрутизацію, стан, обробку помилок і вхід із серверною частиною. Для нашого прототипу це збільшує обсяг роботи. |
| Razor Pages + невеликі фрагменти JavaScript | Сторінки та REST API розміщуються в одному ASP.NET Core проєкті; форми й перевірка введення використовують засоби цього стеку; менше технологій і кроків збирання, простіше інтегрувати та показати прототип. | Звичайні переходи завантажують нову сторінку; збереження стану між екранами потребує окремого рішення. Часткові оновлення та їхні помилки потрібно обробляти JavaScript; зі зростанням складності такого коду перевага простоти зменшується. |
| ASP.NET Core MVC + невеликі фрагменти JavaScript | Той самий стек ASP.NET Core; серверні сторінки та REST API можуть бути в одному проєкті; явне розділення контролерів, моделей і представлень. | Для наших форм і окремих сторінок потрібно узгоджувати контролери та представлення; часткові оновлення так само потребують JavaScript. Для поточного обсягу додаткове розділення не дає вирішальної переваги над Razor Pages. |
| Blazor: Interactive Server | Компоненти й обробники подій на C#; інтерактивні оновлення без повного перезавантаження сторінки; не потрібно завантажувати середовище .NET у браузер. | Потребує активного з'єднання SignalR і зберігання стану компонентів на сервері; розриви з'єднання впливають на взаємодію. Додає обробку відновлення з'єднання, яка не потрібна для звичайних сторінок із запитами до REST API. |
| Blazor: Interactive WebAssembly | Інтерактивні компоненти на C# виконуються в браузері; стан інтерфейсу можна підтримувати на клієнті й отримувати дані через REST API. | Початкове завантаження включає середовище .NET та код компонентів; додаються клієнтський проєкт і узгодження його роботи з API. Для простого перегляду прев'ю й лайків ці витрати не дають потрібного нам спрощення. |

## Рішення (Decision Outcome)

Обрано **Razor Pages у Web App із невеликими фрагментами vanilla JavaScript**, щоб спростити систему та навчальний проєкт. Сторінки фотографа й клієнта, REST API та інтеграція з ASP.NET Core Identity належать одному ASP.NET Core проєкту. Окремий SPA-проєкт і клієнтський фреймворк не додаються.

MVC теж задовольняє ці умови, але Razor Pages групує сторінку та її обробники в одному місці, що зручніше для нашого набору форм і галерей. Компонентна інтерактивність Blazor не є необхідною для цих сценаріїв, тому додавати її режими виконання та керування станом недоцільно в поточному обсязі.

Клієнту важливо швидко переглядати прев'ю, бачити результат лайка та відправити вибір. Для цього достатньо серверної сторінки галереї з JavaScript-запитами до REST API: лайк і прогрес обробки можна оновлювати без повного перезавантаження сторінки. SPA саме по собі не гарантує швидшого завантаження фото; розмір прев'ю й спосіб їх завантаження потрібно враховувати за будь-якого варіанта.

REST API зі Swagger зберігається як частина Web App. Обробники Razor Pages і контролери REST API мають використовувати спільну логіку операцій та перевірки доступу; правила роботи з галереями й вибором не повинні дублюватися або існувати лише в сторінках. Архітектуру сторінок і роль `PageModel` описано в [матеріалі Microsoft про Razor Pages](https://github.com/dotnet/AspNetCore.Docs/blob/main/aspnetcore/razor-pages/index.md).

### Наслідки (Consequences)

#### Переваги

- **Менший обсяг розробки:** команда підтримує один проєкт для сторінок і REST API, без окремого клієнтського фреймворку та процесу його збирання. Більше часу залишається на основний сценарій, обробку фото й узгодженість даних.
- **Простіші інтеграція та запуск:** сторінки, REST API й інтеграція з Identity використовують один Web App. Це зменшує кількість частин, які потрібно узгоджувати й запускати для демо.
- **Достатня інтерактивність для відбору фото:** невеликі JavaScript-запити дозволяють оновлювати лайки й прогрес без повного перезавантаження сторінки, зберігаючи просту основу інтерфейсу.

#### Недоліки та ризики

- **Втрата стану під час переходів:** звичайні переходи завантажують нову сторінку; без окремого збереження клієнт може втратити позицію перегляду або налаштування відображення. Потрібний для продовження відбору стан слід явно зберігати й відновлювати.
- **Зростання складності JavaScript:** якщо інтерактивних дій стане багато, окремі обробники лайків, прогресу та помилок буде складніше підтримувати. Скрипти потрібно розділяти за відповідальністю; за появи складного стану між екранами рішення варто переглянути.
- **Дублювання правил:** обробники Razor Pages і контролери REST API можуть почати по-різному перевіряти доступ або змінювати вибір. Для запобігання цьому вони мають використовувати спільну логіку операцій та серверні перевірки доступу.
- **Витрати на можливий перехід на SPA:** доведеться створити клієнтський проєкт, перенести відображення, маршрутизацію, форми та стан інтерфейсу, перевірити повноту REST API й доповнити відсутні операції. Також потрібно налаштувати збирання та розміщення клієнтських файлів, узгодити автентифікацію й захист запитів; за різних джерел розміщення — налаштувати CORS. Наявність REST API полегшує перехід, але не робить його автоматичним: перевірки доступу й обробку помилок потрібно перевірити з новим інтерфейсом.

Рішення варто переглянути, якщо інтерфейс потребуватиме складного стану між багатьма екранами. Для поточного відбору фото витрати на SPA не виправдовують додаткової складності.
