# ADR-002: Окремий Worker і черга замість моноліту

## Контекст і проблема (Context and Problem Statement)

Головна навантажена операція PicPick — створення прев'ю з вотермаркою. Фотограф завантажує 300–700 фото за раз, зокрема RAW. За NFR-201 один Worker має обробити 300 JPEG не довше ніж за 10 хвилин, а 300 RAW — не довше ніж за 25 хвилин, тобто обробка зйомки триває хвилини, а не секунди. При цьому сайт має залишатися швидким для інших фотографів і клієнтів, а збій під час обробки не повинен губити фото (NFR-202).

Потрібно вирішити, де виконувати обробку і як вона пов'язана з Web App.

## Розглянуті варіанти (Considered Options)

1. **Моноліт.** Усе в одному ASP.NET Core застосунку, обробка фото у фоновому потоці Web App.
2. **Web App + окремий Worker + черга RabbitMQ.** Web App ставить задачу в чергу, Worker на Python забирає її й обробляє.
3. **Web App + окремий Worker з прямим HTTP-викликом.** Web App викликає API Worker для кожного фото, без черги.

| Варіант | Переваги | Недоліки |
|---|---|---|
| Моноліт | Один проєкт, один стек, простіше запускати й налагоджувати; немає мережевої взаємодії між сервісами | Обробка 500 фото забирає CPU і пам'ять у сайту, і сторінки сповільнюються для всіх; падіння під час обробки RAW зачіпає весь застосунок; масштабувати можна лише все разом; обробка RAW у .NET складніша, ніж у Python |
| Worker + черга | Запит фотографа не чекає на обробку; ресурси й паралельність обробки обмежуються окремо від сайту; Worker масштабується окремо (більше копій — швидше); задачі чекають у черзі, якщо Worker недоступний; для обробки зображень обрано зручний стек | Більше компонентів; потрібно узгоджувати базу й чергу; складніше налагоджувати, бо одна операція проходить через кілька сервісів |
| Worker + прямий HTTP | Окремий сервіс без брокера; менше компонентів, ніж із чергою; балансування між кількома Worker можна доручити балансувальнику навантаження | Прямий HTTP-виклик сам по собі не зберігає задачу: якщо Worker недоступний, її треба десь надійно зберегти й повторити. Повтори, обмеження паралельності й балансування між Worker доводиться забезпечувати окремо — фактично частково відтворювати те, що вже дає брокер |

## Рішення (Decision Outcome)

Обрано **варіант 2: Web App + окремий Worker на Python + черга RabbitMQ.**

**Чому окремий сервіс.** Обробка фото — важка й довга операція. Окремий Worker ізолює процес обробки та дозволяє незалежно обмежувати його ресурси (CPU і пам'ять контейнера) і паралельність. Його можна запустити в кількох копіях, а падіння одного з них не зачіпає Web App. На одній машині, як у прототипі, конкуренція за CPU і RAM зберігається; виконання NFR-201 перевіряється навантажувальним тестом. У цільовій архітектурі Worker і Web App можуть працювати на окремих машинах.

**Навіщо черга, а не HTTP.** Черга розв'язує Web App і Worker у часі. Web App кладе задачу й одразу відповідає фотографу, не чекаючи обробки. Якщо Worker зайнятий або впав, задача чекає в черзі й не губиться. Кілька Worker самі розбирають задачі з однієї черги, кожен бере нову, щойно звільнився. Збереження задач, повторну доставку й розподіл навантаження брокер дає готовими, а з прямим HTTP їх довелося б будувати окремо. Результат Worker повертає через другу чергу — Чергу подій.

**Чому Python.** Для зображень і RAW у Python є зрілі бібліотеки: Pillow, pillow-heif, rawpy (LibRaw). У C# для RAW довелося б шукати менш поширені обгортки. Це плюс для обробки, але мінус для команди: два стеки, дві мови й окремі залежності.

### Наслідки (Consequences)

#### Переваги

- Запит на завантаження не чекає на обробку, а ресурси Worker можна обмежити, щоб обробка сотень фото не сповільнювала сайт. Чи досягнуто цього, перевіряє навантажувальний тест за NFR-201.
- Обробку можна прискорити, додавши ще один контейнер Worker, без змін у коді.
- Фото не губляться при збоях Worker або тимчасовій недоступності RabbitMQ (NFR-202).

#### Недоліки

- **Більше компонентів.** RabbitMQ треба запускати, налаштовувати й стежити за ним.
- **Складніше налагоджувати.** Одне завантаження проходить через Web App, MinIO, RabbitMQ і Worker. Щоб знайти помилку, потрібні логи всіх сервісів з однаковим ідентифікатором фото.
- **Узгодженість даних.** Збереження фото в базі й постановку задачі в чергу треба зробити надійними разом, а повторну доставку задачі — безпечною. Ці механізми описано в сценаріях concurrency п.6.
- **Два стеки.** Команді потрібно підтримувати і .NET, і Python.
