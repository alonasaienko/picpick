# CS-101: одночасне оновлення статусу галереї

**Зона:** A. **Авторка:** Юлія. **Патерн:** Оптимістичне блокування (Optimistic Concurrency Control).

## Ситуація

У галереї 300 фото: 298 уже завершено, а два останні ще обробляються. У цьому сценарії одна копія Web App має два незалежні споживачі Черги подій, які обробляють повідомлення паралельно, кожен зі своїм DbContext і транзакцією. RabbitMQ майже одночасно доставляє їм два останні результати; обробники мають оновити фото й перевести Gallery з `Processing` у `Ready`, коли завершено всі фото.

## Проблема

Без узгодження кожен обробник може побачити лише власне оновлення: 299 завершених фото і одне ще в обробці. Обидва залишать галерею в `Processing`, хоча після їхніх записів усі 300 фото вже завершені. Нових подій більше не буде, тому без окремого виправлення галерея залишиться в `Processing`: фотограф не зможе створити посилання для клієнта (FR-301) чи фіналізувати її (FR-106).

## Патерн

**Оптимістичне блокування:** обробник читає версію запису й записує зміни лише тоді, коли версія не змінилася. Якщо інший обробник уже оновив запис, поточна операція відкочується й повторюється на свіжих даних. Наперед блокувати галерею для читання не потрібно.

Джерела: [Microsoft — Optimistic concurrency](https://learn.microsoft.com/en-us/ef/core/saving/concurrency), [PostgreSQL 16 — Read Committed](https://www.postgresql.org/docs/16/transaction-iso.html#XACT-READ-COMMITTED). В архітектурі вже обрано EF Core: поле `version` налаштовується як concurrency token, а конфлікт під час `SaveChanges` спричиняє `DbUpdateConcurrencyException`. Обробник відкочує всю транзакцію й повторює її зі свіжим DbContext, як показано нижче умовним SQL.

## Sequence-діаграма

Показано два обробники одного компонента Web App, кожен зі своєю транзакцією PostgreSQL. Worker уже передав результати в Чергу подій, як у [флоу зони B](../04-architecture/flow-zone-b.md).

```mermaid
sequenceDiagram
    participant Events as Черга подій (RabbitMQ)
    participant First as Web App (обробник 1)
    participant Second as Web App (обробник 2)
    participant DB as PostgreSQL

    Events--)First: Результат для фото 299
    Events--)Second: Результат для фото 300
    par Транзакція 1
        First->>DB: BEGIN, прочитати version, оновити Photo 299,<br/>порахувати завершені фото
        DB-->>First: version = 7, завершено 299 із 300
    and Транзакція 2
        Second->>DB: BEGIN, прочитати version, оновити Photo 300,<br/>порахувати завершені фото
        DB-->>Second: version = 7, завершено 299 із 300
    end
    First->>DB: UPDATE Gallery: Processing, version = 8<br/>WHERE version = 7, COMMIT
    DB-->>First: 1 рядок, зміни збережено
    First->>Events: ack після COMMIT
    Second->>DB: UPDATE Gallery WHERE version = 7
    DB-->>Second: 0 рядків, версія вже змінилася
    Second->>DB: ROLLBACK усієї транзакції 2,<br/>перечитати чинність Gallery
    DB-->>Second: Поточний стан або відсутність галереї
    alt Gallery = Processing, термін чинний
        Second->>DB: BEGIN, прочитати version = 8,<br/>повторити оновлення Photo 300 і підрахунок
        DB-->>Second: Завершено 300 із 300
        Second->>DB: UPDATE Gallery: Ready, version = 9<br/>WHERE version = 8, COMMIT
        DB-->>Second: 1 рядок, Gallery.Status = Ready
        Second->>Events: ack після COMMIT
    else Галерею видалено, прострочено або закрито
        Second->>Second: Не відновлювати дані,<br/>прев'ю підлягає очищенню за FR-203
        Second->>Events: ack, результат більше не застосовується
    end
```

## Як застосовано в нашій системі

- **Компоненти:** Web App обробляє результати з RabbitMQ і записує їх у PostgreSQL; Worker не пише в БД. Назви відповідають [High-level Architecture](../03-srs/high-level-architecture.md).
- **Дані:** для Gallery пропонується технічне поле `version` — ціле число. Це рішення для майбутньої моделі даних, не готова реалізація. Окремий лічильник не потрібний: завершеними вважаються Photo зі статусом `Ready` або `Failed`; `Uploaded` і `Processing` ще очікують завершення.
- **Транзакція:** прочитати версію й перевірити чинність галереї; застосувати результат поточної спроби обробки фото; для `Ready` зберегти PhotoPreview; порахувати незавершені фото; умовно оновити Gallery та збільшити `version`. Версія збільшується при кожному новому результаті, навіть якщо Gallery залишається `Processing`.
- **Умовне оновлення:** `UPDATE galleries SET status = :nextStatus, version = version + 1 WHERE id = :id AND version = :oldVersion AND status = 'Processing' AND expires_at > clock_timestamp()`. Якщо змінено 0 рядків, відкотити **всю** транзакцію, включно з Photo і PhotoPreview; потім перечитати галерею. Для звичайного конфлікту повторити операцію, для видаленої, простроченої чи вже закритої галереї — не застосовувати результат.
- **Гарантія:** стан фото та рішення про Gallery фіксуються разом; конфлікт версій спричиняє повний відкат і повтор із паузою, а підтвердження події надсилається після COMMIT або перевірки, що результат більше нечинний.
- **Повторні доставки:** їх безпечне застосування за NFR-202 має деталізуватися окремо в зоні B (ситуація «Збій воркера» у [тасці #34](https://github.com/alonasaienko/picpick/issues/34), документа ще немає), тому механізм Idempotent Consumer тут не описується й не резервується.

Усі операції, що змінюють набір або стан фото, також мають оновлювати версію Gallery в тій самій транзакції: завантаження, видалення та ручний повтор обробки. Нове завантаження може знову перевести `Ready` у `Processing`; гарантія стосується одного завершення поточної обробки, а не одного переходу за весь час існування галереї.

## Компроміси

- **Чому обрано:** для навчального сценарію обмежуємо паралельність двома споживачами. 300 фото — це загальний обсяг галереї, а не 300 одночасних транзакцій. Перевірка версії доступна в уже обраному EF Core й дозволяє показати виявлення конфлікту та повний повтор транзакції.
- **Ризик і ціна:** потрібні поле версії, повтори та повторні підрахунки. Результати однієї галереї змінюють один рядок, тому транзакції з однаковою прочитаною версією конфліктують навіть для різних фото. Два споживачі обмежують навантаження, але не гарантують рідкісних конфліктів: при надходженні результатів поспіль повтори можуть бути частими й збільшувати затримку.
- **Альтернатива:** `SELECT FOR UPDATE` перед читанням і підрахунком послідовно обробляє результати однієї галереї без повторної роботи через конфлікт версії. Якщо вимірювання покажуть багато повторів, для цієї операції доцільніше обрати його; оптимістичне блокування не заявляється швидшим. Сам UPDATE також може короткочасно блокувати рядок.

## Перевірка результату (для захисту)

Це перевірка майбутньої реалізації з PostgreSQL і RabbitMQ; поточні заглушки API її не виконують.

- **Як відтворити:** запустити в одній копії Web App два незалежні споживачі Черги подій, підготувати 298 завершених і два незавершені фото. Зупинити обидва обробники після читання однакової версії, потім дозволити їм застосувати два останні результати. Окремо повторити тест з одним `Failed` та виміряти кількість конфліктів і час завершення для всіх 300 результатів із двома споживачами. Перевірки повторної доставки й збою до/після COMMIT належать до сценарію зони B, зазначеного вище.
- **Очікуваний стан:** обидва результати збережені, фото в `Uploaded`/`Processing` немає, Gallery має `Ready`; 299 `Ready` і 1 `Failed` також дають `Ready`.
- **Як перевірити:** у PostgreSQL звірити статуси фото та Gallery; у журналі побачити відкат конфліктної транзакції й повтор зі свіжою версією. Повторити з видаленням або завершенням терміну галереї: пізній результат не відновлює даних чи доступу.
