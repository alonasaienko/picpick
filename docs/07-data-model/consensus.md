# Консенсус у PicPick

**Консенсус** — узгодження одного рішення кількома вузлами, навіть коли частина з них недоступна або повідомлення затримуються. Наприклад, вони мають погодитися, хто є лідером і які записи вже підтверджені. [Raft](https://raft.github.io/) використовує вибори лідера та реплікований журнал: у кластері з трьох вузлів для більшості потрібні два. Власний Raft чи Paxos у PicPick не реалізуємо.

## Де потрібна згода

| Місце | Що узгоджується | Як це досягається в PicPick |
|---|---|---|
| Копії Web App, очищення [CS-102](../06-concurrency/cs-102-expired-gallery-cleanup.md) | Яка копія виконує поточний прохід | Усі звертаються до одного primary PostgreSQL за тим самим advisory lock. Одна отримує роль, інші пропускають прохід. Це централізована координація, а не окремий алгоритм консенсусу між Web App; таблиці лідерів немає |
| Primary і резервна репліка PostgreSQL | Який сервер має право запису і які транзакції збережені | Для еталонного AWS-розгортання з [ADR-003](../04-architecture/adr/003-cloud-serverless.md) використовуємо Amazon RDS for PostgreSQL Multi-AZ. RDS підтримує синхронну standby-репліку в іншій зоні доступності та керує failover і недопущенням двох доступних для запису primary (fencing); Web App не обирає primary самостійно |
| Репліки Черги задач і Черги подій у RabbitMQ | Лідер кожної черги й порядок підтверджених повідомлень | Amazon MQ з еталонного AWS-розгортання [ADR-003](../04-architecture/adr/003-cloud-serverless.md) for RabbitMQ у кластерному розгортанні має три вузли. Для RabbitMQ 3.13 і новіших він підтримує quorum queues: задаємо `x-queue-type=quorum`, три репліки. RabbitMQ використовує Raft і більшість із двох реплік. Лідер тут — репліка черги, а не Worker |

## Розділення мережі та split-brain

**Split-brain** виникає, коли ізольовані частини системи обидві вважають себе головними й приймають суперечливі записи. Під час розділення мережі обираємо збереження узгодженості, навіть ціною тимчасової недоступності операції.

- **Очищення Web App:** без зв'язку з PostgreSQL копія не починає прохід, а поточний припиняє за CS-102. Новий лідер з'являється після звільнення старої сесії. Уже надіслане видалення в MinIO може завершитися пізніше, тому воно має допускати повтор, а ключі файлів не використовуються повторно. Advisory lock не робить MinIO частиною транзакції бази.
- **PostgreSQL:** перемикання й fencing виконує RDS Multi-AZ, а не Web App. При обриві з'єднання застосунок припиняє записи й очищення, потім підключається заново через той самий endpoint RDS до нового primary. Advisory locks не переносяться: копії Web App повторно змагаються за роль. Синхронна standby-реплікація захищає підтверджені записи, але не усуває перерву доступності під час failover.
- **RabbitMQ:** частина без більшості не може обрати лідера quorum queue й підтверджувати нові записи. Частина з більшістю продовжує роботу; без більшості черга недоступна до відновлення зв'язку. Publisher confirms та ручний ack усе одно потрібні, а повторні доставки не зникають: їх обробляють [CS-201](../06-concurrency/cs-201-competing-consumers.md) і [CS-202](../06-concurrency/cs-202-transactional-outbox.md).

## Що реалізуємо самі

| У Web App | В інфраструктурі |
|---|---|
| Отримати/звільнити advisory lock, припинити роботу при втраті ролі, безпечно повторити очищення | PostgreSQL забезпечує виключність блокування й звільняє його при завершенні сесії |
| Відновити з'єднання через endpoint RDS, повторювати дозволені операції | RDS for PostgreSQL Multi-AZ забезпечує синхронну реплікацію, failover та fencing |
| Налаштувати quorum queues, publisher confirms, ack і обробку повторів | Amazon MQ керує кластером RabbitMQ, а RabbitMQ виконує Raft і реплікацію черг |

У поточному прототипі [compose.yaml](../../compose.yaml) уже піднімає PostgreSQL, RabbitMQ і MinIO, але Web App і Worker до них ще не підключені, тому перелічені механізми ще не виконуються. Для мінімального Compose достатньо по одному вузлу; це не дає відмовостійкості кластера. RDS Multi-AZ та кластер Amazon MQ описують цільовий AWS-варіант ADR-003, який ще не розгорнуто. AWS є еталоном для документації; остаточний провайдер визначається за умовами ADR.

## Як перевірити після реалізації

1. Одночасно запустити очищення у двох Web App: лише один отримує роль; після зупинки його сесії роль переходить іншому.
2. У тестовому RDS Multi-AZ ініціювати керований failover: Web App відновлює з'єднання через endpoint RDS і заново отримує advisory lock; записи виконуються лише в чинний primary.
3. У тестовому RabbitMQ із трьох вузлів ізолювати один: два продовжують роботу quorum queue, один — ні. Зупинити ще один: без більшості публікації не підтверджуються; після відновлення повідомлення не губляться, можливі повтори обробляються.

Джерела: [PostgreSQL 16 — Advisory Locks](https://www.postgresql.org/docs/16/explicit-locking.html#ADVISORY-LOCKS), [RDS Multi-AZ](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZSingleStandby.html), [Amazon MQ — кластерне розгортання](https://docs.aws.amazon.com/amazon-mq/latest/developer-guide/rabbitmq-broker-architecture.html), [підтримка quorum queues](https://docs.aws.amazon.com/amazon-mq/latest/developer-guide/quorum-queues.html).
