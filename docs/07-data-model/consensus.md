# Консенсус у PicPick

**Консенсус** — узгодження одного рішення кількома вузлами, навіть коли частина з них недоступна або повідомлення затримуються. Наприклад, вони мають погодитися, хто є лідером і які записи вже підтверджені. [Raft](https://raft.github.io/) використовує вибори лідера та реплікований журнал: у кластері з трьох вузлів для більшості потрібні два. Власний Raft чи Paxos у PicPick не реалізуємо.

## Де потрібна згода

| Місце | Що узгоджується | Як це досягається в PicPick |
|---|---|---|
| Копії Web App, очищення [CS-102](../06-concurrency/cs-102-expired-gallery-cleanup.md) | Яка копія виконує поточний прохід | Усі звертаються до одного primary PostgreSQL за тим самим advisory lock. Одна отримує роль, інші пропускають прохід. Це централізована координація, а не окремий алгоритм консенсусу між Web App; таблиці лідерів немає |
| Primary і репліка PostgreSQL у цільовому розгортанні з високою доступністю | Який сервер має право запису і які транзакції збережені | Один primary приймає записи, репліка відтворює WAL. Потокова реплікація сама не обирає primary: перемикання та ізоляцію старого primary забезпечує керований сервіс або готовий HA-механізм, а не Web App. Конкретний сервіс ще не обрано |
| Репліки Черги задач і Черги подій у RabbitMQ | Лідер кожної черги й порядок підтверджених повідомлень | Для цільового кластера пропонуються quorum queues із трьома репліками. RabbitMQ використовує Raft: для підтвердження публікації та нового лідера потрібна більшість. Лідер тут — репліка черги, а не Worker |

## Розділення мережі та split-brain

**Split-brain** виникає, коли ізольовані частини системи обидві вважають себе головними й приймають суперечливі записи. Під час розділення мережі обираємо збереження узгодженості, навіть ціною тимчасової недоступності операції.

- **Очищення Web App:** без зв'язку з PostgreSQL копія не починає прохід, а поточний припиняє за CS-102. Новий лідер з'являється після звільнення старої сесії. Уже надіслане видалення в MinIO може завершитися пізніше, тому воно має допускати повтор, а ключі файлів не використовуються повторно. Advisory lock не робить MinIO частиною транзакції бази.
- **PostgreSQL:** не можна підвищувати репліку до primary лише тому, що один Web App не бачить старий сервер. Спершу HA-механізм має заборонити записи старому primary (fencing), і лише тоді відкрити новий для запису. Якщо є сумнів, хто primary, записи й очищення зупиняються. Advisory locks не переносяться на новий primary: копії Web App повторно змагаються за роль. За асинхронної реплікації можливі втрати останніх транзакцій; синхронна реплікація зменшує цей ризик, але без доступної синхронної репліки може затримати COMMIT і не замінює fencing.
- **RabbitMQ:** частина без більшості не може обрати лідера quorum queue й підтверджувати нові записи. Частина з більшістю продовжує роботу; без більшості черга недоступна до відновлення зв'язку. Publisher confirms та ручний ack усе одно потрібні, а повторні доставки не зникають: їх обробляють [CS-201](../06-concurrency/cs-201-competing-consumers.md) і [CS-202](../06-concurrency/cs-202-transactional-outbox.md).

## Що реалізуємо самі

| У Web App | В інфраструктурі |
|---|---|
| Отримати/звільнити advisory lock, припинити роботу при втраті ролі, безпечно повторити очищення | PostgreSQL забезпечує виключність блокування й звільняє його при завершенні сесії |
| Записувати тільки в чинний primary, повторювати дозволені операції після відновлення з'єднання | Керований HA-сервіс забезпечує перемикання PostgreSQL та fencing |
| Налаштувати тип черг, publisher confirms, ack і обробку повторів | RabbitMQ виконує Raft і реплікацію quorum queues |

У поточному прототипі немає підключених PostgreSQL, RabbitMQ і MinIO, тому перелічені механізми ще не виконуються. Для мінімального Docker Compose достатньо по одному вузлу; це не дає відмовостійкості кластера. Три вузли RabbitMQ та HA PostgreSQL — пропозиція для цільового розгортання, не твердження про вже наявну інфраструктуру.

## Як перевірити після реалізації

1. Одночасно запустити очищення у двох Web App: лише один отримує роль; після зупинки його сесії роль переходить іншому.
2. У тестовому HA PostgreSQL ізолювати primary: новий приймає записи лише після fencing старого, Web App відновлює з'єднання й заново отримує advisory lock.
3. У тестовому RabbitMQ із трьох вузлів ізолювати один: два продовжують роботу quorum queue, один — ні. Зупинити ще один: без більшості публікації не підтверджуються; після відновлення повідомлення не губляться, можливі повтори обробляються.

Джерела: [PostgreSQL 16 — Advisory Locks](https://www.postgresql.org/docs/16/explicit-locking.html#ADVISORY-LOCKS), [реплікація](https://www.postgresql.org/docs/16/warm-standby.html), [failover і захист від двох primary](https://www.postgresql.org/docs/16/warm-standby-failover.html), [RabbitMQ 3.13 — Quorum Queues](https://www.rabbitmq.com/docs/3.13/quorum-queues).
