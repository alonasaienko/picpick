# Конвенція формату помилок

Правила, за якими **всі** ендпоінти REST API PicPick повертають помилки. Таблиці помилок зон (`zone-a.md`, `zone-b.md`, `zone-c.md`) посилаються на цей документ і не повторюють його.

## 1. Формат тіла помилки

Кожна помилка повертається у форматі **Problem Details** ([RFC 9457](https://www.rfc-editor.org/rfc/rfc9457), який замінив RFC 7807) з типом вмісту `application/problem+json`. ASP.NET Core підтримує цей формат вбудовано (`ProblemDetails`, `ValidationProblemDetails`).

| Поле | Звідки | Що містить |
|---|---|---|
| `type` | стандарт | Посилання на опис типу помилки. За нашою конвенцією це зафіксоване посилання на опис відповідного HTTP-коду: розділ RFC 9110, а для 429 — RFC 6585. RFC 9457 цього не вимагає, це наше рішення: конкретну помилку визначає `errorCode` |
| `title` | стандарт | Короткий опис типу помилки, однаковий для всіх її випадків: «Галерею не знайдено» |
| `status` | стандарт | HTTP-код, такий самий, як у відповіді |
| `detail` | стандарт | Пояснення саме цього випадку для людини: «Не можна завантажити фото в галерею зі станом Finalized» |
| `instance` | стандарт | Шлях запиту, у якому сталася помилка: `/api/galleries/42/photos`. Без query string і без секретних значень: `Token` у маршруті замінюється на `{token}`, наприклад `/api/share-links/{token}/likes`. Допускається безпечний URI на основі `traceId` |
| `errorCode` | **наше** | Стабільний машинний код помилки (див. розділ 2). Клієнтський код орієнтується саме на нього |
| `traceId` | **наше** | Ідентифікатор запиту. Фотограф може передати його команді, а ми знайдемо запит у журналах |
| `errors` | **наше**, лише для валідації | Які поля невалідні і чому (див. розділ 4) |

`title` і `detail` — для людини, їх можна переформулювати. `errorCode` — для програми, після оголошення він не змінюється. Текст повідомлень — українською, як і інтерфейс.

## 2. Коди помилок (`errorCode`)

- Стиль **UPPER_SNAKE_CASE**, як у [глосарії](../glossary.md).
- Код починається з **назви сутності** з глосарія, якої стосується помилка: `GALLERY_…`, `PHOTO_…`, `SHARE_LINK_…`, `SELECTION_…`. Далі йде, що сталося: `GALLERY_NOT_FOUND`, `PHOTO_FORMAT_NOT_SUPPORTED`, `SELECTION_ALREADY_SUBMITTED`.
- Загальні помилки, не прив'язані до сутності, мають фіксовані коди без префікса: `VALIDATION_FAILED`, `UNAUTHENTICATED`, `RATE_LIMIT_EXCEEDED`, `INTERNAL_ERROR`.
- Кожна зона перелічує свої коди в таблиці свого файлу `zone-X.md`. Один код означає одну ситуацію у всьому API.

## 3. Коли який HTTP-код

| Код | Коли | Приклад у PicPick | `errorCode` |
|---|---|---|---|
| **400** Bad Request | Запит **зламаний**: його неможливо прочитати за контрактом API. Некоректний JSON, відсутнє обов'язкове поле, неправильний тип, рядок довший за ліміт DTO | `POST /api/galleries` без поля `name` або з `expiresAt: "завтра"` | `VALIDATION_FAILED` |
| **401** Unauthorized | Користувача не автентифіковано: немає cookie входу, він прострочений або вхід не вдався | Запит до `/api/galleries` без входу; неправильний пароль у REST API (FR-102) | `UNAUTHENTICATED` |
| **403** Forbidden | Користувач відомий і має доступ до ресурсу, але **ця дія** йому заборонена | Клієнт за чинним `ShareLink` намагається отримати архів оригіналів (FR-208), який доступний лише фотографу | `…_FORBIDDEN`, напр. `PHOTO_ORIGINALS_FORBIDDEN` |
| **404** Not Found | Ресурс не існує **або належить іншому фотографу** | `GET /api/galleries/42`, коли галереї 42 немає або вона чужа | `GALLERY_NOT_FOUND` |
| **409** Conflict | Запит коректний, але **поточний стан** ресурсу не дозволяє дію | Завантаження фото в галерею `Finalized`; повторна відправка вибору; повтор обробки фото зі статусом `Ready` | `GALLERY_FINALIZED`, `SELECTION_ALREADY_SUBMITTED`, `PHOTO_NOT_FAILED` |
| **422** Unprocessable Content | Запит **прочитано**, але значення порушують правила предметної області | `expiresAt` у минулому або далі ніж через 30 діб (FR-103); файл не JPEG/PNG/HEIC/RAW або більший за ліміт (FR-202) | `GALLERY_EXPIRES_AT_INVALID`, `PHOTO_FORMAT_NOT_SUPPORTED` |
| **429** Too Many Requests | Перевищено ліміт частоти запитів | Забагато спроб входу або завантажень за короткий час | `RATE_LIMIT_EXCEEDED` |
| 500 Internal Server Error | Непередбачена помилка сервера | Виняток у коді, недоступна база даних | `INTERNAL_ERROR` |

**400 чи 422.** Просте правило: якщо для перевірки достатньо подивитися на сам запит і схему DTO (атрибути `[Required]`, `[MaxLength]`, тип поля), це **400**. Якщо потрібні правила предметної області — поточний час, вміст файлу, кількість фото в галереї, — це **422**. В обох випадках невалідні поля перелічуються в `errors`.

**403 чи 404.** Коли галерея існує, але належить іншому фотографу, повертаємо **404**, а не 403. Відповідь 403 підтвердила б, що галерея з таким ідентифікатором існує, і дозволила б перебором знаходити чужі галереї. Тому для чужого й неіснуючого ресурсу відповідь однакова: той самий код, `errorCode` і текст (NFR-102, FR-105). 403 використовуємо лише тоді, коли користувач уже законно бачить ресурс, але конкретна дія йому не дозволена.

**Виняток: пакетне завантаження фото.** За FR-201–FR-202 кожен файл пакета перевіряється окремо: коректні файли приймаються, а відхилені повертаються окремим списком. Тому:
- якщо прийнято **хоча б один** файл, відповідь — звичайна **200 OK** зі списком прийнятих фото і списком відхилених файлів; для кожного відхиленого вказано індекс у запиті, ім'я файлу, `errorCode` і повідомлення. Problem Details тут не використовується;
- якщо відхилено **всі** файли, нічого не збережено, і відповідь — **422** Problem Details з `errorCode` `PHOTO_ALL_FILES_REJECTED` і причиною для кожного файлу в `errors` (див. розділ 4). Стан галереї не змінюється;
- якщо відхилено **весь запит** ще до перевірки файлів (понад 50 файлів чи 1 ГБ — 422, галерея `Finalized` — 409, чужа галерея — 404 тощо), відповідь — Problem Details за загальними правилами цього розділу.

**409 чи 422.** 422 — проблема в **даних запиту**: якщо виправити дані, запит пройде. 409 — проблема в **стані ресурсу**: той самий запит пройшов би раніше, але зараз стан не дозволяє.

**429.** Відповідь містить заголовок **`Retry-After`** з кількістю секунд до наступної дозволеної спроби і тіло Problem Details з `RATE_LIMIT_EXCEEDED`. Ліміти й політики описано в задачі «Rate limiting: відповідь 429» та [Identity Management](../03-srs/identity.md).

**410 (опційно).** Може використовуватися для простроченого чи відкликаного посилання клієнта, якщо зона C вирішить відрізняти його від неіснуючого. Рішення — у таблиці `zone-c.md`.

## 4. Помилки валідації

Для 400 і 422 через невалідні поля додається поле `errors`: об'єкт, де ключ — назва поля в camelCase (як у запиті), а значення — масив повідомлень. Так клієнт може показати помилку біля конкретного поля форми.

Для файлів ключ — **індекс файлу в запиті**, починаючи з нуля: `files[0]`, `files[1]` тощо, у тому порядку, у якому їх надіслав Браузер. Ім'я файлу не підходить як ключ, бо в одному пакеті можуть бути два `IMG_0001.jpg`. Ім'я передається лише як додаткова інформація в тексті повідомлення:

```json
"errors": {
  "files[3]": ["IMG_0001.jpg: формат не підтримується."],
  "files[7]": ["IMG_0001.jpg: файл більший за 30 МБ."]
}
```

## 5. Приклади

**422 — некоректний термін дії галереї:**

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.21",
  "title": "Дані не відповідають правилам",
  "status": 422,
  "detail": "Термін дії галереї має бути в майбутньому і не далі ніж через 30 діб.",
  "instance": "/api/galleries",
  "errorCode": "GALLERY_EXPIRES_AT_INVALID",
  "traceId": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
  "errors": {
    "expiresAt": ["Дата вже настала."]
  }
}
```

**404 — галерею не знайдено (і для неіснуючої, і для чужої):**

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.5",
  "title": "Галерею не знайдено",
  "status": 404,
  "detail": "Галерею не знайдено або вона вам недоступна.",
  "instance": "/api/galleries/42",
  "errorCode": "GALLERY_NOT_FOUND",
  "traceId": "00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01"
}
```

**429 — забагато запитів** (заголовок відповіді `Retry-After: 30`):

```json
{
  "type": "https://tools.ietf.org/html/rfc6585#section-4",
  "title": "Забагато запитів",
  "status": 429,
  "detail": "Перевищено ліміт запитів. Повторіть через 30 секунд.",
  "instance": "/api/galleries/42/photos",
  "errorCode": "RATE_LIMIT_EXCEEDED",
  "traceId": "00-6e0c63257de34c92bf9efcd03927272e-0f1e2d3c4b5a6978-01"
}
```

## 6. Чого не можна повертати в помилці

У тілі помилки **ніколи** не повертаються:
- стектрейси, назви класів і тексти винятків;
- SQL-запити, назви таблиць, повідомлення PostgreSQL;
- внутрішні шляхи, назви бакетів і ключі файлів у MinIO;
- `Token` із `ShareLink` у будь-якому полі, зокрема в `instance`; хеші паролів, email інших фотографів;
- ознака того, чи існує акаунт або чужа галерея.

**Чому.** Такі деталі не допомагають користувачу, зате підказують нападнику, як влаштована система: яка база, які таблиці, де лежать файли, які email зареєстровано. Деякі з них — персональні дані (NFR-102). Для 500 повертаємо лише загальний текст і `traceId`, а повну інформацію про виняток записуємо в журнал сервера. Глобальну обробку винятків описано в задачі «Глобальна обробка помилок у Web App».
