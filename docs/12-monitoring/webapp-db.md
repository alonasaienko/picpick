# Моніторинг Web App і PostgreSQL

Prometheus збирає метрики, Grafana показує дашборд, Alertmanager надсилає сповіщення команді, яка обслуговує систему. Джерела — вбудовані метрики ASP.NET Core через OpenTelemetry та `postgres_exporter`. Опис охоплює Web App і PostgreSQL за [глосарієм](../glossary.md).

Це план моніторингу. У [Program.cs](../../src/webapp/Program.cs) є `GET /health` із відповіддю `ok`. Підключення PostgreSQL, OpenTelemetry, експортерів і алертів ще потрібно реалізувати. Залежності Web App наведено у [WebApp.csproj](../../src/webapp/WebApp.csproj).

## Збір і дашборд

- Початковий інтервал збору й перевірки алертів — 15 с. Grafana показує доступність джерел, запити/с, p95, частки 5xx і 429, з'єднання та довгі запити PostgreSQL.
- Метрики ASP.NET Core збираються для Razor Pages і REST API, включно з відповідями middleware та rate limiting. З HTTP-показників виключаємо `/health`, майбутній endpoint готовності, `/metrics`, статичні файли й тестові запити `demoError`. Завантаження фото показуємо окремо від звичайних запитів.
- Labels містять лише контрольовані значення — середовище, копію сервісу, метод, шаблон маршруту, статус відповіді, назву БД і стан з'єднання. Маршрут має вигляд `/api/galleries/{id}`, для невідомого маршруту — `unmatched`. Повний URL, токен ShareLink, email, IP, id фотографа/галереї та SQL-текст у labels не потрапляють.
- `/metrics` та експортери доступні лише мережі моніторингу. Для PostgreSQL потрібен окремий обліковий запис із мінімальними правами читання статистики.

## Метрики

| ID | Метрика | Тип (counter / gauge / histogram) | Виміри (labels) | Ресурс | Як збирається | Навіщо |
|---|---|---|---|---|---|---|
| TM-101 | Доступність джерел і PostgreSQL | gauge | `job`, `instance`, середовище | Web App, PostgreSQL | Prometheus `up` для кожної очікуваної копії Web App та `postgres_exporter`. Експортер додатково дає `pg_up` — успішність підключення до БД. Значення 1/0 | Виявити недоступний Web App, БД або збір метрик, зокрема без користувацького трафіку |
| TM-102 | Кількість завершених HTTP-запитів | counter | копія Web App, метод, шаблон маршруту, HTTP-статус, клас `normal` / `upload` | Web App | Кількість спостережень (`_count`) гістограми `http.server.request.duration` через OpenTelemetry. `rate` за 5 хв дає запити/с | Бачити навантаження й знаменник для часток помилок |
| TM-103 | Тривалість HTTP-запитів, секунди | histogram | ті самі, що TM-102 | Web App | Вбудована `http.server.request.duration`. Prometheus рахує p95 за 5 хв через `histogram_quantile` із сумарних швидкостей bucket усіх копій. Додати bucket рівно 0,5 с | Перевіряти швидкість сторінок і API за NFR-201 |
| TM-104 | Частка HTTP 5xx, % | gauge, обчислений показник | середовище, клас запиту, шаблон маршруту | Web App | 100 × приріст кількості відповідей 500–599 / приріст усіх відповідей TM-102 за ті самі 5 хв. Спершу підсумувати прирости всіх копій | Виявляти помилки сервера та залежностей |
| TM-105 | Частка HTTP 429, % | gauge, обчислений показник | середовище, клас запиту, шаблон маршруту | Web App | 100 × приріст відповідей 429 / приріст усіх відповідей TM-102 за ті самі 5 хв | Помітити, що ліміти заважають користуванню або відбувається сплеск запитів |
| TM-106 | Використані з'єднання PostgreSQL, % | gauge | копія PostgreSQL, БД, стан з'єднання | PostgreSQL | `postgres_exporter` читає `pg_stat_activity` та налаштування лімітів. Для алерту — кількість клієнтських з'єднань у всіх станах і БД / доступний звичайним користувачам бюджет `max_connections` після віднімання зарезервованих слотів | Завчасно виявляти наближення до ліміту БД. Пул кожної копії Web App також має вкладатися в сумарний бюджет |
| TM-107 | Поточні запити PostgreSQL, що виконуються понад 5 с | gauge | копія PostgreSQL, БД | PostgreSQL | Додатковий колектор `postgres_exporter` рахує рядки `pg_stat_activity` зі `state = active`, віком `query_start` понад 5 с, без власного запиту збору й фонових процесів. Передає тільки кількість | Шукати довгі запити й очікування блокувань під час зростання p95 |

TM-104 і TM-105 обчислюються з counter, окремі лічильники для них не потрібні. При нульовій кількості запитів частка та p95 показують «немає запитів». Втрата джерела показує «немає даних» і перевіряється окремим алертом. Назви й labels після експорту в Prometheus потрібно звірити з обраною версією OpenTelemetry та `postgres_exporter`.

## Алерти

Усі алерти мають тип **пороговий**. `for` означає, що умова виконується безперервно протягом зазначеного часу. Для часток і p95 використовуємо ковзне вікно 5 хв та щонайменше 100 завершених запитів у цьому вікні. Це початковий захист від шуму на малому трафіку. Доступність перевіряється незалежно від кількості запитів.

| ID | Алерт і поріг | Тип | Критичність | Звідки поріг | Mitigation |
|---|---|---|---|---|---|
| AL-101 | Очікувана копія Web App або експортер має `up = 0` чи втратила часовий ряд, або `pg_up = 0`. `for: 2m` | Пороговий, доступність | Critical | 2 хв — початковий компроміс між швидким виявленням і коротким перезапуском. Втрата збору потребує перевірки, бо приховує стан сервісу | Виконати кроки AL-101 нижче |
| AL-102 | TM-104 > 5%, `for: 5m`, щонайменше 100 запитів за 5 хв | Пороговий, частка | Critical | Початкове припущення. Стійкі помилки більш ніж у 1 з 20 запитів суттєво заважають роботі | Виконати кроки AL-102 нижче |
| AL-103 | TM-103 p95 > 0,5 с для звичайних сторінок/API, `for: 5m`, щонайменше 100 таких запитів за 5 хв | Пороговий, затримка | Warning | 500 мс — NFR-201 п.3. Вікно, мінімум запитів і `for` — початкові налаштування моніторингу | Перевірити TM-106/107, блокування й останні зміни. Обмежити джерело зайвого паралелізму, оптимізувати повільний запит. Перевірити відновлення p95 |
| AL-104 | TM-105 > 10% окремо для `normal` або `upload`, `for: 10m`, щонайменше 100 запитів відповідного класу за 5 хв | Пороговий, частка | Warning | Початкове припущення. Десятихвилинна стійкість відсіює короткий сплеск пакетного завантаження | Зіставити маршрут і час із журналами та `Retry-After`. Перевірити частоту UI-запитів і сплеск навантаження. Скоригувати клієнтські повтори або обґрунтовано переглянути ліміт |
| AL-105 | TM-106 > 80% доступного бюджету з'єднань, `for: 10m` | Пороговий, насичення ресурсу | Warning | Початковий резерв 20% для сплесків і службових дій. Потребує перевірки з фактичним `max_connections` та кількістю Web App/Worker | Перевірити стани з'єднань, довгі транзакції та сумарні пули. Усунути витік чи зайвий паралелізм, звільнити з'єднання. Перевірити запас до ліміту після змін |

За кількох копій втрата однієї може означати зменшення резерву. AL-101 консервативно сповіщає команду й про такий випадок. Prometheus має знати перелік очікуваних targets. Перевірка відсутнього ряду порівнює цей перелік із наявними рядами, зокрема коли target помилково вилучено з discovery.

### Дії для AL-101

1. Визначити відсутній target. Перевірити контейнер/процес, мережу й endpoint метрик. Окремо перевірити відповідь Web App та можливість підключення до PostgreSQL, щоб установити масштаб збою.
2. Якщо зламався лише збір, відновити експортер, його права чи конфігурацію. Якщо недоступний Web App — відновити процес або відкотити проблемне розгортання. Для БД перевірити мережу, ліміти та події керованого failover за [R-I2-1](../08-resiliency/zone-a.md). Використати штатний endpoint БД для нового з'єднання.
3. Якщо після 5 хв від спрацювання немає відновлення або причина невідома, залучити іншого відповідального за Web App/БД. Після відновлення перевірити безпечне читання та запис тестових даних і повернення метрик. Перерваний запис перевірити читанням перед повтором.

### Дії для AL-102

1. Знайти час початку, проблемні маршрути й копії Web App. Зіставити помилки з журналами за `traceId` відповідно до [конвенції помилок](../05-error-handling/conventions.md). Перевірити AL-101, з'єднання та блокування PostgreSQL.
2. Усунути встановлену причину. Для регресії після розгортання відкотити зміну. Для збою залежності відновити її за RMA. Результат запису, перерваного з'єднанням, перевірити перед повторним надсиланням.
3. Якщо протягом 10 хв після спрацювання частка не знизилася або є підозра на втрату даних, залучити іншого відповідального за застосунок/БД. Перевірити роботу проблемного сценарію та падіння частки 5xx нижче порога.

Alertmanager групує повідомлення за середовищем та алертом, додає копію сервісу й посилання на дашборд. Сповіщення йде команді обслуговування через узгоджений командний канал. Під час підтвердженого збою БД повторні AL-102 з тієї самої причини можна приглушити, зберігаючи їх на дашборді.

## Зв'язок із вимогами та перевірка

- [NFR-201 п.3](../03-srs/zone-b-processing.md) задає 95% запитів за ≤ 500 мс під час обробки еталонного набору. Для TM-103 об'єднуємо звичайні сторінки й API всіх копій, виключаючи upload. Не усереднюємо p95 різних копій. Межа bucket 0,5 с дозволяє також прямо перевірити частку запитів до 500 мс. Повний приймальний тест виконується на еталонному навантаженні.
- NFR-201 п.1–2 і п.4 задають час обробки, прискорення та пам'ять Worker. Їх перевіряє моніторинг Worker і черг. Ці HTTP-метрики допомагають побачити вплив фонової обробки на Web App.
- [NFR-102](../03-srs/zone-a-accounts.md) і [NFR-301](../03-srs/zone-c-client.md) враховано через обмежені labels і захист endpoint метрик. TM-106/107 підтримують розбір відмов I-2 у [RMA зони A](../08-resiliency/zone-a.md). Діагностичний поріг довгого SQL-запиту 5 с походить із початкового припущення R-I2-2.
- Перевірити на тестовому середовищі зупинку Web App, недоступність БД та експортера, зникнення очікуваного target, серію 5xx, повільні відповіді, 429 і заповнення бюджету з'єднань. Переконатися, що алерт надходить після `for` і закривається після відновлення. За нульового трафіку мають працювати перевірки доступності.
- Додати окремий endpoint готовності Web App, який перевіряє отримання з'єднання з його пулу й `SELECT 1` із коротким тайм-аутом. Поточний `/health` показує відповідь процесу. `pg_up` перевіряє шлях від експортера до БД, тому готовність Web App потрібно перевірити окремо під час реалізації.

Пороги 5%, 10%, 80%, вікна й строки ескалації — запропоновані стартові значення. Їх потрібно уточнити після навантажувального тесту та перших спостережень.
