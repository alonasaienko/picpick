# RMA workbook: зона A

Аналіз I-1 (Браузер → Web App) та I-2 (Web App → PostgreSQL) з [CID-діаграми](README.md#cid-діаграма). Ймовірність: Низька / Середня / Висока; критичність: 1 — незручність, 5 — втрата даних або зупинка всієї системи. Оцінки якісні, а наведені цілі відновлення потрібно перевірити під навантаженням; це не виміряні SLA.

У прототипі є спільний формат помилок і rate limiting; PostgreSQL, Identity та відновлення після failover ще не підключені. Поведінка UI й інфраструктури нижче описує цільову систему. Реакції та повтори — за [конвенцією помилок](../05-error-handling/conventions.md#9-реакція-клієнта).

## I-1. Браузер → Web App: сторінки та REST API

| ID | Режим відмови | Причина | Вплив | Ймовірність | Критичність | Виявлення | Запобігання | Відновлення |
|---|---|---|---|---|---|---|---|---|
| R-I1-1 | **Недоступний:** жодна копія Web App не відповідає | Падіння процесів, невдале розгортання або збій мережі | Сторінки не відкриваються, API не має відповіді або шлюз повертає 502/503; це не обов'язково Problem Details | Середня | 5 | Зовнішня перевірка HTTPS; відсутність здорових копій у балансувальнику; журнали перезапусків | 2+ копії за балансувальником і поступове оновлення за [ADR-003](../04-architecture/adr/003-cloud-serverless.md); автоматичний перезапуск контейнера | 1. Відкотити невдале розгортання або запустити здорову копію. 2. Перевірити доступність і журнали. Ціль — до 2 хв після запуску відновлення; при мережевій аварії — до усунення її причини. UI зберігає форму, повторює GET обмежено; POST автоматично не повторює |
| R-I1-2 | **Повільний:** запит зависає на 30 с | Перевантаження Web App, очікування бази або довге блокування | Замість результату — індикатор очікування; користувач може натиснути кнопку повторно | Середня | 3 | Тривалість запитів p95, число активних запитів, журнали тайм-аутів | Не чекати створення прев'ю в HTTP-запиті (FR-201); обмежити паралельність, блокувати повторне натискання під час надсилання | Для звичайного читання пропонується клієнтський тайм-аут 30 с: прибрати індикатор і показати банер. GET — до 3 повторів із backoff за конвенцією. Тайм-аут у браузері не доводить скасування серверної операції: після POST спершу перевірити результат читанням, а не автоматично надсилати його знову. Для завантаження файлів потрібен окремий тайм-аут за розміром; сервер відновиться після усунення перевантаження |
| R-I1-3 | **Перевантаження:** надто багато запитів | Часті натискання, надто часте опитування або багато запитів з однієї IP | API повертає 429 `RATE_LIMIT_EXCEEDED` із `Retry-After`; дія тимчасово недоступна | Середня | 2 | Частка 429, значення `Retry-After`, кількість запитів за політиками | Реальна політика `default` 120 запитів/хв на IP; без накладання запитів опитування. Ліміти входу — окремі за Identity Management | UI показує відлік, призупиняє опитування й надсилання; повтор лише після `Retry-After`, не раніше. Час очікування визначає заголовок, а не фіксована пауза. При постійному навантаженні перевірити джерело запитів; не вимикати ліміт |

## I-2. Web App → PostgreSQL: дані акаунтів і галерей

| ID | Режим відмови | Причина | Вплив | Ймовірність | Критичність | Виявлення | Запобігання | Відновлення |
|---|---|---|---|---|---|---|---|---|
| R-I2-1 | **Недоступний:** PostgreSQL не приймає з'єднання | Падіння primary, failover RDS, обрив мережі | Вхід, перевірка доступу й робота з галереями недоступні; API повертає безпечний 500 `INTERNAL_ERROR` із `traceId`. Закритий доступ не обходиться | Середня | 5 | Помилки з'єднання й `traceId`; події RDS; окрема перевірка готовності з доступом до БД | RDS for PostgreSQL Multi-AZ за ADR-003, короткі операції й обмежені повтори безпечних читань | 1. Перевірити події RDS і доступність мережі. 2. Дочекатися керованого failover, відновити з'єднання через endpoint RDS. 3. Перевірити читання й запис тестових даних. AWS наводить типові 60–120 с для failover, але це не гарантія; мережевий збій може тривати довше. Результат перерваного запису перевірити перед повтором |
| R-I2-2 | **Повільний:** SQL довго виконується | Немає індексу, довга транзакція блокує рядок, завеликий запит | Повільний список галерей чи прогрес, можливий 500 після серверного тайм-ауту | Середня | 3 | Тривалість SQL, блокування в `pg_stat_activity`, журнали повільних запитів; початковий поріг діагностики — 5 с | Індекси з [моделі зони A](../07-data-model/entities-zone-a.md) та `(gallery_id, status)` зони B; короткі транзакції, обмежений час виконання SQL | Знайти блокувальну транзакцію, виправити запит або індекс; після помилки відкотити транзакцію й звільнити з'єднання. Ціль — нормальна швидкість протягом 1 хв після усунення причини, а не повтор того самого важкого запиту без паузи |
| R-I2-3 | **Вичерпано пул:** немає вільного з'єднання | З'єднання не звільняються, надмірний паралелізм або завелика кількість копій Web App | Нові запити чекають, потім отримують 500; проста база може бути доступна, але запити не проходять | Середня | 4 | Час очікування пулу, зайняті з'єднання, помилки отримання з'єднання; порівняти з `pg_stat_activity` | Звільняти DbContext і з'єднання після операції; сумарний розмір пулів усіх копій узгодити з бюджетом БД, залишивши резерв для очищення й адміністрування | Припинити джерело витоку чи зайвого паралелізму, звільнити з'єднання; за потреби поступово перезапустити Web App. Ціль — до 2 хв після усунення причини. Не збільшувати пули без перевірки ліміту PostgreSQL |
| R-I2-4 | **Перервана транзакція:** збій до COMMIT | PostgreSQL чи Web App упав під час оновлення Photo та Gallery або стався конфлікт версій | Часткове оновлення не зберігається; прогрес може затриматися, операція користувача не завершена | Низька | 3 | Журнал відкатів, виняток БД чи `DbUpdateConcurrencyException`; версії й статуси в PostgreSQL | Photo, PhotoPreview і рішення про Gallery — в одній транзакції за [CS-101](../06-concurrency/cs-101-gallery-status.md). Задача на обробку — з Photo через [CS-202](../06-concurrency/cs-202-transactional-outbox.md) | Якщо COMMIT не відбувся, PostgreSQL відкочує всі зміни транзакції. Конфлікт CS-101 повторюється зі свіжими даними; непідтверджена подія повертається через RabbitMQ після відновлення. Ціль — наступний цикл обробки після відновлення залежності; зовнішні файли не відкочуються SQL-транзакцією й очищуються за retention policy |
| R-I2-5 | **Невідомий результат COMMIT:** запис міг зберегтися | З'єднання обірвалося після надсилання COMMIT, але до отримання підтвердження | UI може показати помилку, хоча Gallery вже створено чи фіналізовано; сліпий повтор POST може створити зайву галерею | Низька | 4 | Помилка з'єднання на COMMIT; зіставлення журналу запиту, поточних записів і версій після відновлення | Успіх повідомляти лише після підтвердження; не повторювати неідемпотентні записи автоматично. Завершену фіналізацію дозволено безпечно повторити за FR-106 | Після відновлення перечитати Gallery, якщо її id відомий; для створення без отриманого id оновити список і запропонувати фотографу перевірити результат. Не вважати збіг назви доказом тієї самої операції. Повтор створення — лише після перевірки користувачем; ціль — можливість перевірити стан одразу після відновлення БД |

`GET /health` прототипу перевіряє лише відповідь Web App, а не готовність PostgreSQL. Окрема перевірка БД, метрики та алерти — план для [моніторингу #113](https://github.com/alonasaienko/picpick/issues/113). Пороги 30 с і 5 с та цілі 1–2 хв вище — початкові робочі припущення для перевірки, не нові NFR.

## Перевірка після реалізації

1. Зупинити всі копії Web App, потім запустити одну: перевірити повідомлення UI, збереження форми та відсутність автоматичного повтору POST. Окремо затримати GET на 30 с і перевищити ліміт частоти.
2. У тестовому середовищі відключити БД, затримати SQL і вичерпати невеликий тестовий пул: перевірити обмежене очікування, безпечний 500 і відновлення після звільнення ресурсів.
3. Перервати транзакцію до COMMIT: Photo і Gallery не мають часткових змін. Окремо розірвати з'єднання на COMMIT: перевірити обидва можливі результати й відсутність сліпого повтору створення Gallery.
